### Proposed audience rule

`PROPOSED — CONTROLLER APPROVAL REQUIRED`

- Dayova is intentionally directed at learners in grades 10–12 and is **not
  intentionally directed at children under 13**.
- Registration must reject an `under_13` age result. Google Play target audience
  remains `13+`; the store answer, onboarding gate, terms, policy, and support
  procedure must say the same thing.
- Core app processing for learners aged 13–17 does not rely on consent where it
  is necessary to provide the requested service.
- Optional PostHog analytics is disabled by default for everyone. Learners aged
  16–17 may opt in themselves. Learners aged 13–15 may participate only after a
  separately implemented, verifiable holder-of-parental-responsibility
  authorization. Until that exists, analytics remains disabled for them.
- Do not use a full birth date for educational personalization. DAY-347 must
  either justify a necessary age consumer or remove it. Prefer a minimal,
  versioned age-assurance result (`under_13`, `13_15`, `16_17`, `adult`) over
  retaining the raw date when the product can meet its obligations without it.

This is deliberately conservative. GDPR Article 8 sets 16 as the default age at
which a child can consent to information-society processing and allows Member
States to lower it no further than 13. The controller or counsel must confirm
the German-law application before approving analytics for minors.

- `expo-dev-client`-associated `SYSTEM_ALERT_WINDOW`, exported AndroidX test

  remove them or obtain a documented security/release justification before the

- React Native/Fresco/Hermes namespaces under `com.facebook`; no Meta social or

## 8. Proposed retention and deletion schedule

`PROPOSED — CONTROLLER/COUNSEL APPROVAL REQUIRED`

“Delete” below means removal from the live Dayova store and every linked
processor, not merely hiding a row. “Anonymous” means the result cannot

## 9. Analytics consent and withdrawal implementation contract

DAY-361 is not complete until all of these are true:

1. Do not mount a network-active `PostHogProvider` before server-authorized
   consent. Use `disabled: true` or lazy initialization as the primary boundary;
   `defaultOptIn: false` is defense in depth, not sufficient by itself. Explicitly
   disable feature-flag preload, surveys, remote config and default person
   properties. No `identify`, `capture`, SDK queue write or analytics network
   request occurs first.
2. The learner sees a German, age-appropriate choice after core account access,
   with purpose, exact data categories, PostHog, EU/transfer statement, 90-day
   retention, voluntary nature, and withdrawal route. “Accept” and “decline” have
   equal prominence.
3. Convex is the authority for `policyVersion`, `status`, `decidedAt`,
   `withdrawnAt`, age band, and authorization method. The local SDK state mirrors
   it; a second device cannot silently re-enable analytics.
4. Consent covers only the allowlisted contract in `src/lib/analytics.ts`.
   Autocapture, lifecycle events, session replay, surveys, feature flags, raw
   error capture, names, email, phone, birth date, avatar, school type/name,
   notes, filenames, content, answers and transcripts remain off.
5. Withdrawal is available in Settings at any time, takes effect immediately,
   calls PostHog opt-out, explicitly purges queued events/logs and local
   identifiers using a tested supported storage boundary, and creates an
   observable idempotent server job to delete the PostHog person and events.
   Do not rely on `reset()` to purge queues.
6. The UI reports pending/completed cleanup without restoring capture. Deletion
   retries use an opaque internal job ID, not raw PII in logs.
7. Native tests cover first launch, decline, accept, offline, second device,
   13–15 without parental authorization, 16–17, withdrawal, re-consent, account
   deletion, and upgrade from a legacy tracking-enabled build.

PostHog documents that React Native tracking is enabled by default unless
`defaultOptIn` is false, that the opt state is persistent, and that events queue
on device while offline. Inspection of installed SDK `4.50.0` additionally shows
that remote configuration paths are not the same as capture opt-out and that
`reset()` preserves event/log queues. Its person/event deletion is asynchronous,
so the pipeline must poll and record completion rather than equating an API
`202` with erasure.

## 10. Account deletion implementation contract

The current Settings action calls Clerk user deletion and logout only. It does
not prove deletion of Convex rows, R2 objects, PostHog events, RevenueCat mapping,
other Clerk sessions, local notification schedules, SDK queues, or secure caches.
It therefore does not meet this contract or the Apple/Google account-deletion
requirements.

DAY-183/DAY-358 must implement this state machine:

1. Require recent server-verified reverification and explicit confirmation.
2. Create one idempotency key and atomically mark the Dayova user `deleting`,
   denying all new product access on every device.
3. Revoke all Clerk sessions and delete the identity through a trusted server
   path. Client-only `user.delete()` is not the authority.
4. Enumerate and delete/anonymize all 23 Convex tables, every R2 object, PostHog
   person/events, RevenueCat identifier mapping, notification state, and local
   state. Include legacy transcript and school-name data.
5. Record only opaque step status, attempts, next retry and the applicable
   retention exception. Jobs must be retryable and must never restore access.
6. Verify external asynchronous deletion. Complete within 30 days or escalate
   before the deadline; tell the learner the actual status.
7. Explain that deleting Dayova does not cancel an App Store/Play subscription
   and provide the relevant store-management link before confirmation.
8. Offer the same complete request path from the public deletion page required
   by Google Play. Email support may assist but cannot be the only in-app flow.

## 15. Change-control rule

A pull request that adds a table/field, SDK, permission, processor, data
destination, analytics property/event, AI prompt input, local cache, or retention
exception must update this contract and the Notion approval record before store
submission. CI should eventually compare the schema/direct dependencies/native
permissions/analytics allowlist to an approved manifest so drift becomes a
failing release check rather than a manual discovery.
