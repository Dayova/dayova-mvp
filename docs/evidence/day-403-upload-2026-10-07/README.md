## Final policy

- PDFs and other supported documents: **25 MiB per file**.
- Images: **7 MiB per file**; timetable uploads retain their existing 7 MiB rule.
- All attached school material combined: **25 MiB per learning plan**. Existing plans above this total require removing or reducing material before processing. No existing file is automatically deleted.
- Client selection (files, gallery, camera) and backend downloaded-byte validation use the same policy. A single byte above a boundary is rejected with the applicable limit.

The initially explored 40 MiB PDF / 40 MiB total proposal is **not shipped**. Three successive SDK requests with actual HTTP transport reached approximately 632–637 MiB RSS during that investigation. Mocking fetch had understated the peak. The smaller policy restores #656's original document target and adds a conservative aggregate bound. This is a measured interim product limit, not a universal maximum for every document.

### Actual SDK plus HTTP memory checks

`convex/learningMaterialMemory.integration.test.ts` bundles the production preparation helper and production batch scheduler into a child Node process with `--max-old-space-size=384`. It sends three SDK requests through the production transport to an actual local HTTP server in a separate process. Storage grants/downloads and provider responses are synthetic; SDK serialization, HTTP encoding, backpressure, and client memory are real. No forced garbage collection. The server's memory is excluded, as an external provider would be.
